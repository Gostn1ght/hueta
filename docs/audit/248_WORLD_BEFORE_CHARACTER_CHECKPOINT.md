# Refuse inventory checkpoints until world removals are committed

While tracing TASK-E02-005 payout to durable character save, the shared checkpoint path exposed an earlier P0 inventory consistency defect relevant to TASK-E11-001 and E00 loot preservation. character_save_actor explicitly continued after an unsuccessful world save with pending world item removals. A newer character image could therefore contain picked-up items while the last durable world still contained those same items. This is a code path and crash-image risk, not a newly reproduced player's crash.

The synchronous path now returns false if world_store_save_now fails or world_store_takes_committed still reports an outstanding pickup generation. It refuses before progress/items/actor snapshot/revision mutation. Background saves retain their existing request-and-defer behavior; nonpersistent worlds and actors without pending pickups retain the previous path. A successful later world commit permits capture. No destructive fallback, forced disconnect or ownership bypass is added.

cluster_move already rejects a failed checkpoint, removes its prepared ticket and source-leaving marker, and does not reach admission_depart. Disconnect cleanup already waits for the character/account save before releasing the actor and lease; host stop waits for character saves too. Existing actual transfer/disconnect tests remain necessary. No claim is made that independent account-wallet updates and all cross-store transactions are now atomic.

check-native-character-world-order.py compiles the actual admission prefix of character_save_actor and actual world-take/request/generation helpers in Windows CI. The capture/commit tail is an explicit boundary hook. It verifies invalid actors, absent level/server, background deferral, repeated failed saves, nominal save success without a newer commit generation, successful retry/destination, later pickups, actor isolation and no-persistence compatibility. A one-item durable-image model checks that failure does not write a second durable copy. It is not a full ALife save, OS crash or game acceptance test.

Both Foundation CPU Windows and full native workflows invoke the new fixture. No native/game/GPU execution occurs locally, no live data/install/publication changes. PDA durable intent/receipt and credit→character-money recovery remain open; a Lua-only retry could duplicate an ambiguously committed transfer and is not substituted for that work.
